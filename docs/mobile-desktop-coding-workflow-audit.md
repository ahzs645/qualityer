# Desktop and mobile coding workflow audit

Date: 2026-10-03. Scope: read-only source inspection of transcript coding and existing analysis workflows. This document contains recommendations and acceptance criteria, not new browser, device, performance, accessibility, or upstream runtime test results. The product was being changed concurrently; findings describe the inspected baseline and must be checked against the resulting implementation. No interview quotations or identifying example data are included.

## Main finding

The app already has exact passage coding, hierarchical codes, multiple applications, coder attribution, passage/case links, analytic memos, comparison, fragment queries, and evidence-linked charts. The immediate gap is the interaction between selecting original text and preserving that selection while using the controls, especially on touch devices. A count of available features does not establish that a researcher can complete the workflow reliably on a phone.

The intended implementation direction communicated during this audit is a turn/logical-line navigator outside the source text container, selection-change detection with explicit confirmation, an exact codepoint range editor, a collapsible mobile codebook, and a bounded bottom passage drawer. These changes are pending verification here. An interview overview and evidence drilldown are also being developed separately.

## What a coding unit means

A meaning unit is the passage the researcher judges relevant to an interpretation. It may be part of a sentence, a whole answer, or several turns. A speaker turn is a useful navigation unit; it is not automatically a theme or claim. A logical source line is delimited by the original newline sequence. A physical line produced by browser wrapping changes with viewport width, font size and zoom and must never become a persistent coding boundary.

Persistent text selections should retain `{documentId, sourceRevision, start, end, text}`, with half-open Unicode codepoint bounds. DOM offsets use UTF-16 and require conversion. Original newlines, combining characters, astral characters, bidirectional text and whitespace must remain recoverable. A logical-line or turn button must select a documented exact source range without injecting its label into the quoted text. Do not trim a researcher-selected passage silently. Whole-turn timestamps describe that turn; they do not establish exact word timing for a partial passage.

## Methodology and analysis workflow

**Open and in-vivo coding.** Support a researcher forming a tentative concept while reading rather than requiring a prebuilt codebook. An in-vivo name comes from the participant's wording but still needs human choice, definition and contextual interpretation. Use code-description/version history for changes in analytic meaning; code renaming alone must not alter original quotations.

**Multiple coding and independent double coding.** Applying several thematic codes to one quote is multiple coding by one person. Independent double coding is separate researchers making their own decisions before comparison. Existing coder layers, blind policy and separately stored consensus support the latter. The interface should distinguish these actions and explain the comparison unit. Exact-span agreement, character-union Jaccard and character-level kappa answer different questions; agreement does not validate the interpretation. Imported coder labels are historical labels, not authenticated identities.

**Memos and reflexivity.** Existing shared project/source/code/passage memos, journals, case memos and citation-linked analytical readings provide useful foundations. The passage action should show its source and exact anchor and flag outdated anchors. Analyst interpretation, procedural notes, code definitions and personal reflexive notes have different purposes even when stored as text. Shared memos must show author/version history; private notes must remain outside shared state, AI evidence, reports and project exchange. Merely mentioning a source with `@source` is a navigable record reference, not an exact evidence citation.

**Retrieval and cross-case comparison.** Preserve an inspectable chain from code/subtree to scoped application table to exact quote to surrounding dialogue. Offer source, case, coder and decision filtering at the relevant step, and keep the scope visible on exports. The Analysis workbench already supports matrix groups, measures and drilldowns; avoid duplicating another unscoped visualization. Whole-source case links and passage-specific case links are different membership rules. A case column overlapping another column need not add to a study total. Coding density or a word cloud does not establish participant prevalence or analytic importance.

**Negative evidence.** Existing theme reading can cite contrasting evidence, passage links can `qualify`/`contradict`, review tasks can preserve related evidence, and the coverage view distinguishes administration from evidence. Improve discovery by letting a researcher pin an uncoded search result as a contrasting passage with a reason, then cite it in a theme memo without pretending it was an original thematic coding. A blank matrix cell is absence of recorded coding in the selected scope, not proof of absence of the phenomenon. Unasked topics, insufficient transcript, silence and explicit disagreement should remain distinct.

**Queries and derived findings.** Whole-application AND/NOT and interval intersection/subtraction must remain explicitly distinct. Frozen query fragments are new researcher decisions with original provenance; they are not original coding IDs or consensus. Literal corpus search must include eligible uncoded passages and retain exact source bounds. Chart/network relationships are descriptive of the declared operator and coding layer, not causality.

## Required rehearsal before claiming completion

Use a disposable project copy and synthetic Unicode/newline cases first, then the authorized private interview without publishing its content. Record actual browser/device versions and separate simulated viewport checks from native touch-device checks.

1. On desktop, select an uncoded partial answer, create/apply an open or in-vivo code, add a second code and memo, then retrieve that exact passage through its subtree and source/case scope. Verify original source text/turns/timestamps remain unchanged.
2. Select across logical lines and speaker turns; revise exact boundaries using the fallback. Resize and zoom. Confirm identical codepoint bounds and quoted text, with no navigator text in the selection.
3. On actual iOS Safari and Android Chrome, adjust native selection handles, confirm text, search codes with the software keyboard, apply and close/reopen the drawer. A Chromium mobile viewport alone cannot certify these gestures.
4. Exercise source changes, remote transcript revisions, reversed/out-of-container selections, stale citations, and competing project revisions. No write may quietly code a substituted quote.
5. Two authenticated coders independently code a common passage and a partial-overlap passage. Check blind visibility, author-specific writes, comparison methods and separately stored reviewer consensus. Same-person multi-code applications must not be called double coding.
6. Find an eligible uncoded counterexample, cite it as a qualification with a reason, then export the analytical memo. Check current/restricted/stale evidence handling and missing timing. Absence of coding must not become automatic negative evidence.
7. Compare matrix/portrait/hierarchy/network drilldowns with declared scope, denominator and measure; test overlapping cases and overlapping regions. Export exact quotation bounds and supplied timestamp provenance in native project/transcript and REFI exchange without fabricating word timing.
8. Test keyboard/focus navigation, readable code labels beyond color, stripe/list alternatives, 200% zoom, reduced-motion preferences and narrow portrait/landscape layouts. Record screen-reader and native-device checks separately; no blanket accessibility claim from source inspection.

Each completed criterion needs its own observed outcome and any limitation. This audit by itself does not demonstrate full feature parity or successful completion of those rehearsals.
